# 轮询花多少代价

面板从 0.1.0 起每 2 秒轮询一次，读到「每 2 秒 6 个 git 进程」时已经是 0.12.0。用户提出这件事并要求验证对 DSH 的影响，于是先量、再定预算、再改。

## 量到的现状（v0.12.0，`safemanage-ui`，面板聚焦空闲）

- 每 2 秒 **6 个 git 进程**：`status`、`rev-parse --show-toplevel`、`config --get-regexp user.*`、`remote`（/status），`symbolic-ref`、`for-each-ref`（/refs）。
- 单轮 HTTP：/status 70–104 ms，/refs 30–48 ms。
- 宿主进程 CPU：**0.75%**（40 秒 CPU 时间差，同一窗口）。
- 轮询只在这个面板是当前主视图时跑；切到对话会卸载，窗口隐藏或有写操作时会暂停——所以它是「打开面板时的代价」，不是常驻背景开销。

## 决定

- **只在窗口聚焦且面板在前台时轮询**。失焦、`visibilityState === 'hidden'`、有写操作进行中：不跑 git；回焦/回前台立刻刷一次。事件驱动，不轮询「要不要轮询」。
- **节拍 3 秒，空闲退避到 10 秒**：连续 3 次 status 签名不变（分支、oid、upstream、ahead/behind、三组计数、条目列表）就退到 10 秒；签名一变、指针进入面板、窗口回焦，立刻回到 3 秒并刷新。
- **每轮只留一条 `git status`**。仓库根、`user.name/email`、remote 名单属于「仓库静态信息」，按仓库路径缓存 **60 秒**（换仓库自然失效；我们的写操作不会改这些）。缓存键是 realpath，不绑 subprocess 服务对象——真实运行时 `ctx.get('subprocess')` 每次拿到的句柄并不保证是同一个，绑对象会一直 miss（这条是实测发现的）。
- **引用树走自己的 10 秒节拍**，或者分支/oid 变了才取；`/refs` 接受客户端刚读到的 `branch`，省掉一次 `symbolic-ref`。
- **不做**：`fs.watch` 监听 `.git`（`index.lock`、`packed-refs` 重写、loose ref 原子替换噪声大，收益不抵复杂度）；把 `/status` 与 `/refs` 合并成一条路由（省的是毫秒级 HTTP，不是进程）。
- **验收数字**（同一 shim 采样 + CPU 时间差）：聚焦空闲 60 秒 ≤ 30 次 git 调用、宿主 CPU ≤ 0.3%；失焦 0 次；换仓库/写操作后的刷新 < 300 ms。

## 结果（v0.13.0，同一仓库、同一窗口、聚焦空闲 40 秒）

| | git 调用 | 宿主 CPU |
| --- | --- | --- |
| 改造前 | 123（3.1/s） | 0.75% |
| 改造后 | 9（0.22/s） | 0.25% |

- 失焦 20 秒：0 次 git 调用；回焦后立即刷新（实测 12 ms 内拿到新仓库状态；换仓库同）。
- 逻辑抽在 `src/client/poll.ts`（签名、退避、引用树节拍），不依赖 DOM，由 built-bundle 契约测试覆盖；宿主的缓存与 `/refs?branch=` 由路由契约测试覆盖（第二次 status 在同一 TTL 内只跑 `git status`）。
- 已知取舍：外部（终端、其他工具）改动的仓库静态信息最多晚 60 秒才反映；分支列表最多晚 10 秒。两者都不影响 diff、改动列表和提交按钮的准确性。
