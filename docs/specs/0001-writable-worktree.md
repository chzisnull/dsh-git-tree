# 可写工作区：正确的改动模型 + 暂存 / 提交

> 目标版本：0.1.1（保真修复，补丁）→ 0.2.0（暂存 / 提交）。
> 已发布：GitHub issue [#1](https://github.com/chzisnull/dsh-git-tree/issues/1)，标签 `ready-for-agent`。本文件是可编辑副本，改动后请同步到 issue。

## Problem Statement

DSH 用户在这个 Git 面板里只能看，不能动。每要暂存一个文件、提交一次，都得离开 Harness 切回终端或 Sourcetree——而面板存在的全部意义就是"在对话旁边把改动处理掉"。一个只能看的面板，在真实工作流里基本不会被打开。

而且它显示的内容并不完全可信：

- 冲突文件直接从列表里消失，用户会误以为工作区是干净的；
- 重命名被渲染成"删除 + 新增"两条，读改动时要自己对；
- 同一文件既有已暂存又有未暂存改动时，只在"工作区"一栏出现一次，用户会以为暂存区里的那份没了；
- diff 是没有结构的等宽文本墙，没有行级底色、没有行号、没有 hunk 边界，读长 diff 很累；
- Agent 改完文件后面板不会自己变，用户得反复点刷新，而它恰恰要陪在 Agent 旁边。

最后，这个插件从没装进任何 DSH profile：`0.1.0` 目前是一个声明，不是一件被验证过的事实。

## Solution

把面板从"只读预览"变成"能处理改动的工作区"，并先补齐它自己承诺过的数据正确性：

1. **装进 desktop profile 并跑通验收清单**，把 0.1.0 变成可验证的事实。
2. **保真修复（0.1.1）**：正确的改动模型——冲突、重命名、双侧改动都按 git 的真实状态呈现；diff 改为宿主编排的结构化 hunk，客户端按行渲染（整行底色、行号、hunk 边界、二进制与重命名提示）；左栏换成真实的本地分支 / 远程 / 标签树；工作区改动在 2 秒内自动刷新；大仓库的列表与 diff 用窗口化渲染保持流畅。
3. **写操作（0.2.0）**：文件级暂存 / 取消暂存（可撤销）、带二次确认的提交、提交结果回执；存在冲突时阻止提交并说明原因。
4. **发布**：本地 link 验证稳定后打 tag、发 npm。

用户在 DSH 里完成"看改动 → 暂存 → 写提交信息 → 提交"的完整闭环，不再为了一次提交切走。

## Implementation Decisions

### 改动模型（数据正确性）

- **状态解析以 porcelain v2 为准，并恢复 git 的真实语义**：不再传 `--no-renames`；解析 `1`（普通改动）、`2`（重命名 / 复制）、`u`（未合并）、`?`（未跟踪）四类记录。rename 记录在 `-z` 模式下路径是两段 NUL 分隔字段（新路径、原路径），解析器必须同时取出。
- **每个条目暴露两侧状态，而不是一个布尔值**：条目携带原始 XY 字母、`staged`（索引侧有改动）、`unstaged`（工作区侧有改动）、`conflicted` 三个派生布尔值。`staged` 与 `unstaged` 可以同时为真——这就是双侧改动，两栏各渲染一次。
- **冲突优先**：`u` 记录归类为 `conflicted`，永远不进"已暂存 / 未暂存"分组，单独一组置顶，并带 git 给出的 XY 冲突组合（如 `UU`、`AA`）。
- **术语与分组统一**：列表分组、diff 请求、撤销记录全部使用"staged / unstaged / conflicted"三个 side 值；一个 entry row 由 `(path, side)` 唯一确定，选中状态也按这个二元组记录。

### 结构化 diff（宿主侧解析）

- **diff 由宿主解析成结构，不把原始文本丢给浏览器**。原因：行级着色、hunk 边界、行号、二进制 / 重命名提示都需要结构；并且未来的 hunk 级暂存需要稳定的 hunk 标识。客户端只渲染，不解析。
- **payload 形状**（决策级）：顶层包含 `path`、`side`、`stats { additions, deletions }`、`binary`、`truncated`；`files[]` 每项含 `oldPath`、`newPath`、`status`（modified/added/deleted/renamed/copied/mode-changed）、`hunks[]`；每个 hunk 含 `header`、`oldStart`、`oldLines`、`newStart`、`newLines`、`lines[]`；每行含 `kind`（context / add / del / meta）、`oldNo`、`newNo`、`text`。
- **解析必须覆盖**：`\ No newline at end of file`、`Binary files … differ`、rename / copy 头（`similarity index`、`rename from`、`rename to`）、mode 变更、`--- /dev/null` 与 `+++ /dev/null`（新增 / 删除）、多文件 diff。
- **渲染行高固定**，为 diff 的窗口化渲染提供前提；行底色使用宿主的 `--dsw-alias-file-diff-*` token，缺失时用 `color-mix()` 从 success / error 派生，不出现硬编码颜色。

### 宿主路由与契约

- 路由集合从 2 条 GET 扩展为：`status`、`diff`（结构化）、`refs`（只读）三条 GET，`stage`、`unstage`、`commit` 三条 POST。
- **写操作统一契约**：JSON body；成功返回 `{ ok: true, ... }`；可预期的领域失败返回 `{ ok: false, error, code }`，并使用 HTTP 语义状态码（400 参数错误、409 状态冲突如"无暂存内容""存在未解决冲突"）；意外异常仍由统一的 guard 兜底，不把异常抛给 HTTP 桥。
- **路径与工作区校验复用现有守卫**：绝对路径、`..`、`~`、`-` 开头、NUL、超长一律在进入 argv 前拒绝；`cwd` 必须落在 workspace 内；所有路径参数放在 `--` 之后；每次写操作最多 500 条路径。
- **命令选择**：暂存用 `git add -A --`；取消暂存用 `git reset --quiet HEAD --`（对工作区无副作用，且不依赖较新的 `restore`）；提交用 `git commit -m <message>`（`-m` 作为单个 argv，不经 shell，多行安全），提交前校验信息非空、长度上限、无未合并条目。
- **不提供 reset --hard、push --force、amend、discard 路由**：本期的写操作面刻意保持最小，破坏性操作留给后续版本并强制确认。
- **提交回执**：返回短 SHA、完整 SHA、提交标题、分支名；提交信息按 git 默认 cleanup（去尾随空白、保留内部换行）处理。
- **refs 路由**：一次 `for-each-ref` 读取本地分支、远程分支、标签，返回名称、是否当前分支、upstream、最近提交标题与时间；本期只展示，不提供 checkout。ahead/behind 用现有 status 数据填充当前分支，其余分支留空。

### 客户端

- **面板变成一个带状态的工作区**：状态存储（status）、选中项（path + side）、diff 存储、撤销栈、轮询器、写操作 in-flight 标记。
- **写操作交互**：entry row hover 显示该侧的动作按钮（暂存 / 取消暂存）；列表组头提供"全部暂存"；动作成功即本地重取 status；失败在行上方显示可关闭的错误提示。
- **撤销**：客户端记录最近一次写操作的逆操作（stage ↔ unstage），提交不在撤销范围。撤销只回放逆操作，不引入服务端 undo 路由。
- **提交区**：显示作者身份（来自宿主 `git config`，缺失时显示提示）、当前分支、暂存文件数、多行信息框、取消 / 提交按钮；无暂存内容或信息为空时按钮禁用；提交前弹出确认对话框（分支 + 文件数 + 信息预览）；成功后清空信息、显示短 SHA 回执 toast 并刷新。
- **冲突横幅**：存在冲突时在列表上方显示说明，提交按钮禁用并解释原因。
- **刷新**：面板可见时每 2 秒轮询 status；文档隐藏、确认框打开或写操作进行中时暂停；窗口重新获得焦点或写操作完成后立即重取。
- **窗口化渲染**：改动列表与 diff 行都按固定行高做窗口化，只渲染可视区域上下缓冲；`truncated` 在列表底部提示。
- **文案**：所有新增可见文案进 en / zh 字典；不新增硬编码字符串。
- **不新增依赖**：客户端仍然只 `require('react')`，构建仍是 esbuild 单文件产物。

### 版本与发布

- 先发 `0.1.1`（保真修复 + 安装验证），再发 `0.2.0`（写操作）；两个版本都在 desktop profile 中验证后打 tag。
- 发布顺序：本地 `link:` 安装 → 验收清单 → tag → `npm publish`。

## Testing Decisions

- **好测试的定义**：只断言外部可观察行为——HTTP 状态码、JSON 契约字段、实际传给 git 的 argv、以及写操作前后的状态迁移；不断言内部函数名、组件结构或 CSS 类名。每个测试只覆盖一个行为，失败信息里带上路由名，让人一眼知道坏在哪。
- **唯一的新测试缝隙：宿主 HTTP 路由边界。** 沿用现有的 `apply()` + 假 context 模式：假 context 收集 `connection.fetch.register` 的 handler，假的 subprocess 记录 argv 并返回预设的 stdout / stderr / exit code。所有新增的解析、校验、argv 构造、冲突拦截、错误映射都通过这个缝隙测试，不新增第二个缝隙。
- **不新建 DOM 测试环境**：客户端行为不引入 jsdom / testing-library（会新增依赖和第二套缝隙）。客户端仍由现有的 bundle contract 测试守住——两条 slot、六条路由名、结构化 diff 的渲染入口、只用主题 token、不操作 `document.body`；视觉与交互通过下面的手工验收清单确认。
- **需要覆盖的宿主行为**：
  - porcelain 解析：普通改动、未跟踪、rename（两段路径字段）、冲突（`u`）、双侧改动派生布尔值、截断上限；
  - 结构化 diff 解析：多文件、多 hunk、行号递增、增删 / 上下文分类、`\ No newline` 标记、二进制、rename 头、新增 / 删除文件、`+N −M` 统计；
  - stage / unstage：argv 形状（`add -A --`、`reset --quiet HEAD --`）、`--` 前置、空数组 / 超限 / 非法路径拒绝、失败映射；
  - commit：冲突存在时 409、信息为空时 400、成功回执字段、`-m` 单 argv 携带多行、无 shell；
  - refs：`for-each-ref` 解析、当前分支标记、空仓库不崩；
  - 所有路由：cwd 越界 403、subprocess 缺失时降级而不抛。
- **先例**：`test/routes.test.mjs` 已经是这个缝隙的范本（假 ctx + 假 subprocess + 逐条断言），新测试沿用同一套构造方式；`test/manifest.test.mjs`、`test/ui-contract.test.mjs` 继续作为清单与 bundle 的护栏。
- **手工验收清单**（记录在 issue 评论里，含 DSH 版本与实测数字）：插件装上后左栏出现 Git 图标；touch 一个文件后 2 秒内列表更新；冲突仓库里冲突文件可见且提交被拦；rename 显示原路径；双侧改动在两栏各出现一次；浅色 / 深色下行底色正确；暂存 3 个文件 → 提交 → `git log -1` 与回执一致；撤销暂存后索引恢复；8000 文件仓库滚动无明显掉帧。

## Out of Scope

- 历史视图（提交列表、泳道、提交详情、搜索）——P3。
- 右侧栏窄面板页签——等主面板提交区定稿后复用。
- hunk 级暂存 / 取消暂存——本 spec 只做文件级；结构化 diff 是为它铺路，但不在本期交付。
- 丢弃改动（discard / checkout --）、amend、push / pull / fetch。
- 分支 checkout、合并、rebase、冲突解决 UI；冲突本期只展示与拦截。
- Agent 工具化：把写操作暴露成 Agent 可调用的工具（本期只保证宿主契约稳定，不注册工具）。
- 多仓库 / 工作区切换、子模块、worktree、Git LFS 特判。
- 语法高亮（diff 仍然只做整行底色）。
- 响应式三形态（≥1200 / 900–1200 / <900）；本期只做列表与 diff 的窗口化，不重做布局断点。

## Further Notes

- 仓库此前没有 `GLOSSARY.md`，本次已补：terminology 以"working copy / index / staged entry / unstaged entry / two-sided change / conflict / rename / hunk / diff line / write operation / undo"为准，spec 与后续代码注释沿用。
- 仓库没有 ADR 目录。本 spec 里"diff 由宿主解析成结构 + 只设一个宿主路由测试缝隙"是一个跨版本难以回退的架构决定，值得一条 ADR；如需要，实施时补 `docs/adr/0001-host-parsed-diff-and-single-test-seam.md`。
- 安装入口按 README 的两种方式之一（`dsh plugin add <路径>` 或 `plugin_manager action=install_bundle`），安装属于一次授权操作；验证结果（图标出现、刷新延迟、8k 文件帧率）要写回 issue，作为 0.1.0 / 0.1.1 的完成证据。
- 冲突只展示不解决，用户在冲突仓库里仍需要终端或 Agent；这是本期有意的边界，README 的状态表需要如实反映。
